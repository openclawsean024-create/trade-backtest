## F1 — Telegram message uses HTML parse_mode without escape (medium)

**Location:** `signal-monitor.js:255-263`

```js
const { telegram_token, telegram_chat_id } = config;
// ...
const body = JSON.stringify({
  chat_id: telegram_chat_id,
  text: messageText,         // ← contains user-supplied symbol
  parse_mode: 'HTML'
});
```

**Why it matters:**
- Telegram interprets `parse_mode: 'HTML'` markup (`<b>`, `<i>`, `<a>`, etc.).
  If `messageText` contains `<` or `>` they will be parsed as markup, not
  rendered literally. Worst-case: a symbol that happens to contain
  `<script>` would attempt to render as a tag (Telegram strips unknown
  tags client-side, but a determined actor could craft markup that
  phishes via Telegram's `<a href="...">` rendering).
- M5's `validateSymbol` rejects `/` but does NOT reject `<` or `>`.
  Symbols in scope today are pure alphanumeric (`BTCUSDT`, etc.) so
  this is latent — but any future expansion to user-supplied symbols
  exposes it.

**Recommended fix (deferred):**
- Either escape `<`, `>`, `&`, `"` before injecting into the HTML body,
- Or switch `parse_mode` to `'MarkdownV2'` and escape Telegram's
  MarkdownV2 special chars (`_*[]()~\`>#+-=|{}.!`),
- Or build the message via Telegram's plain text path (no parse_mode).

**Owner:** backend (signal-monitor is server-side; the `detectSignals`
output is the immediate source of `messageText`).

## F2 — CORS wildcard on public API handlers (medium)

**Location:** `api/klines.js:310-312`, `api/fundamental.js:28-30`

```js
res.setHeader('Access-Control-Allow-Origin', '*');
res.setHeader('Access-Control-Allow-Methods', 'GET, OPTIONS');
res.setHeader('Access-Control-Allow-Headers', 'Content-Type');
```

**Why it matters:**
- Acceptable today: these are public read-only data proxies. No
  credentials are issued or accepted.
- Latent risk: the moment a future version adds cookie-based auth
  (`Access-Control-Allow-Credentials: true`), `'*'` is forbidden by
  spec and the handler will silently leak the user's session to any
  origin that visits.
- Also: allows any third-party site to proxy crypto/stock queries
  through this endpoint (cost amplification attack against upstream
  Binance/Yahoo/CoinGecko rate limits).

**Recommended fix (deferred):**
- Echo the request `Origin` header back instead of `'*'` (allowlist
  the production domain + `localhost:3000` for dev).
- Document in SPEC: "no credentials will ever be issued by these
  endpoints; if that changes, CORS must be re-evaluated".

**Owner:** backend.

## F3 — No rate-limiting or auth on `/api/*` (low)

**Location:** both `api/klines.js` and `api/fundamental.js` entry points.

**Why it matters:**
- Any internet caller can hammer Binance / Yahoo / CoinGecko through
  this proxy. The upstream services have their own rate limits, and
  hitting them will get *this project's* egress IP banned, breaking
  the app for everyone.
- No auth = no per-user throttling possible. Vercel's `@vercel/node`
  does not provide built-in rate limiting; you'd need an edge
  middleware or a separate rate-limit store (Upstash, KV, etc.).

**Recommended fix (deferred):**
- Add Vercel Edge Middleware that rate-limits per source IP (e.g.
  60 req/min).
- Long-term: consider signed tokens for non-public deployment
  scenarios.

**Owner:** devops (middleware) + backend (handler signature changes).

## F4 — Telegram env vars read at config-construction time (low)

**Location:** `signal-monitor.js:21-22, 32-33`

```js
telegram_token: process.env.TELEGRAM_BOT_TOKEN || '',
telegram_chat_id: process.env.TELEGRAM_CHAT_ID || ''
```

**Why it matters:**
- Reading `process.env.TELEGRAM_BOT_TOKEN` at module load captures it
  into the config object that gets `JSON.stringify`'d into logs (if
  any logger is added later) or thrown into error messages.
- Best practice: read env vars at use-site only, not at module init.

**Recommended fix (deferred):**
- Move `process.env` reads into the `sendTelegram` function itself so
  the secret never enters the config object's lifetime.

**Owner:** backend.

## F5 — User-Agent header spoofs a real browser (low)

**Location:** `api/fundamental.js:49`

```js
'User-Agent': 'Mozilla/5.0 (Windows NT 10.0; Win64; x64) ... Chrome/123.0.0.0'
```

**Why it matters:**
- Yahoo Finance's API is not officially public; many client libraries
  spoof a browser UA to bypass detection. If Yahoo tightens ToS
  enforcement, this handler will start returning 403.
- Same pattern in `api/klines.js` (`fetchBinance`, `fetchYahoo`,
  `fetchCoinGecko`) — all use `'User-Agent': 'Mozilla/5.0'`.

**Recommended fix (deferred):**
- Document the dependency on tolerated UA spoofing.
- Plan a graceful failure when upstream starts rejecting (already
  implemented via the source-priority fallback chain in
  `api/klines.js`).

**Owner:** backend.
